# Portfolio credibility design

## Goal

Make the portfolio read as a clear, personal backend engineering portfolio. Keep every public claim within the evidence in the repository README, public source links, project decisions, and explicitly labeled browser models.

## Audience and path

Primary audience: a hiring engineer or technical lead evaluating Adam for PHP/CakePHP backend work. Lead with that work, then show developer tooling and operations as supporting range. Give visitors a direct path to source, selected upstream contributions, and Adam's GitHub profile.

## Content rules

- Separate shipped/public source, active development, prototype, proposal, and undocumented project records.
- Never turn a design goal into a current capability or measured outcome.
- Mark browser-only examples as models, and name what they do not exercise in one short, specific sentence.
- Prefer one concrete source, release, screenshot, or result to a list of architecture buzzwords.
- Preserve accurate limits; remove repeated caveats where one clear status/evidence block suffices.
- Use Czech and English in every user-facing surface, including code-like diagrams.
- Do not invent contact details, metrics, customers, deployments, or source evidence.

## Experience

1. Homepage: direct Czech/English positioning, real project evidence, three selected projects, upstream work, one clearly scoped home-network model, and a GitHub contact path.
2. Project detail: problem, actual implementation/design state, accessible evidence, and one focused next action. Use project-specific current proof and boundary copy.
3. Project groups: describe the page as a grouped index rather than an architecture graph.
4. Supporting pages: correct scope claims, translation, contribution completeness, privacy language, and generated plural forms.

## Visual direction

Keep the existing graphite palette and blue accent. Reduce the dashboard feel with fewer uppercase labels, fewer ornamental arrows/badges, clearer type scale and line length, real product evidence, and more breathing room. Maintain light/dark themes, responsive layouts, and keyboard-readable controls.

## Scope boundary

Local source change only. Do not deploy. Do not fabricate project evidence or add a mail backend without an established address/service.

The map is a curated model, never live telemetry; show service paths and the effect of selecting a failed node. Use the topology coordinates and dependency relationships instead of a card grid. Preserve keyboard access, small-screen readability, reduced-motion preferences, and a text path for assistive technology.

Remove the playground from navigation, sitemap, project cross-links and page content. Keep the old route only as a 301 alias to the network map for existing bookmarks. Link the featured Home Infrastructure card directly to the curated map; avoid a second repetitive homepage callout. Present the maker route as two independent projects with their actual status, not as sequential stages. Keep all nine project records and their bilingual statuses; revise wording only where it improves naturalness, precision or project-specific evidence. Remove repeated filler and avoid claims that imply production use, measured results, live integrations, or complete implementation without evidence.

The owner explicitly asked to proceed, so this direction is the implementation choice. Success means visitors can quickly identify the work, distinguish shipped work from proposals, inspect a coherent and responsive evidence-led site, and explore the network model without being asked to treat a toy as a product. No visual result is called “perfect”; remaining subjective judgments are reported plainly.
